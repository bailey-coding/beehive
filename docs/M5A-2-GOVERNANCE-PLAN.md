## Design

### Migration `m14` (`GOVERNANCE_SQL`, one section, new tables only, `REFERENCES actors` at most)

- `change_classifications(id, entity_type CHECK IN ('issue','spec','candidate'), entity_id, commit_sha TEXT /*candidate rows: the head sha classified*/, change_type CHECK IN (typo-fix, refactor, behavior-change, security-sensitive, dependency-change, infra, schema-migration, oracle-change, unclassified), confidence REAL CHECK 0..1, classifier, inputs_hash, created_at)`; index `(entity_type, entity_id, created_at)`. Append-only; the newest row wins, ties broken by `created_at` then `rowid` (S6).
- `approvals(id, subject_type CHECK IN ('candidate','role_change','policy_change','spec'), subject_id, rung TEXT CHECK (rung IS NULL OR rung IN ('canary','full')) /*NULL for spec, role_change, policy_change rows*/, commit_sha TEXT /*NULL for non-candidate rows*/, content_hash TEXT /*spec rows: sha256 of the approved spec content, computed by the DO*/, approver_eligible INTEGER /*snapshot of membership in E at insert time*/, approver_actor_id REFERENCES actors, decision CHECK IN ('approve','reject'), self_approval INTEGER, reason, created_at)`, with **no unique key on `decision`**: an approver's effective decision is their latest row (rowid), so approve, reject, approve by one approver is legal; redelivery is deduplicated by the Idempotency-Key. For `role_change` / `policy_change`, `subject_id` is the sha256 of the canonical request body. `commit_sha` is the candidate head at approval time; the check requires it to equal `candidates.commit_sha` now, so an approval does not survive a new commit (B2). `rung` is `'full'` in this plan; earlier rungs are not approvable (S6). A reject or approval is superseded only by a new append-only row.
- `near_misses(id, spec_id, candidate_id, reason CHECK IN ('trial_loss','gate_fail','train_drop','slo_rollback','tournament_loss'), rung, lost_to_candidate_id, trial_id, source_ref, evidence TEXT /*JSON*/, complexity_delta REAL, created_at)`, `UNIQUE(candidate_id, reason, source_ref)` with `INSERT OR IGNORE`, where `source_ref` is the trial id, verdict run id, tournament/train id or deployment id. A re-delivered write therefore cannot duplicate a row (S3). Indexes on `(spec_id, created_at)` and `(candidate_id)`.
- `intent_provenance(id, entity_type CHECK IN ('issue','spec'), entity_id, origin CHECK IN ('maintainer','known_agent','external','unknown'), origin_actor_id REFERENCES actors /*NULLABLE*/, source TEXT /*ui, api, agent, github, other: no CHECK, widening a CHECK later needs a rebuild*/, created_via TEXT /*session, admin, master, agent_token, unverified*/, source_issue_id TEXT /*logical reference, specs only*/, basis TEXT /*JSON: how origin was derived*/, created_at)`, `UNIQUE(entity_type, entity_id)`, written by the DO in the same transaction as the issue or spec insert, from the authenticated principal (see Rev 4). m14 also stores `governance.m14_epoch` (the ledger timestamp of the migration) in `metadata`: an entity with no row and `created_at < epoch` is `legacy` = `maintainer`; **no row and `created_at >= epoch` is `unknown` (treated as `external`)**, so a DO rollback below m14 or a skipped write fails closed (S1).
- `governance_events(id, event TEXT /*policy_change, role_change, governance_degraded, break_glass, approval_missing*/, actor_id, asserted_actor_id, subject TEXT, reason TEXT, detail TEXT /*JSON*/, created_at)`, no foreign keys, never purged (like `purge_log`). All system events go here; `entity_history` keeps only per-candidate facts (`approval_missing` on a candidate, type 'candidate') (S2).
- **Dropped from rev 1:** `cost_attributions` and `outcome_links`. Nothing in this plan writes them, so they would violate "every module must be reachable"; adding them later is cheap and additive. The ADR 0005 initiator/executor/reviewer and cost fields move to a later plan (with M5b) (S6).
- Policy lives in the `metadata` table under a **key whitelist** the policy route enforces (so it can never overwrite `schema_version` or the promotion mode): `governance.two_person_mode` (`bootstrap` default | `enforced`), `governance.critical_types` (default `["security-sensitive","dependency-change","infra","schema-migration","oracle-change"]`), `governance.approval_window_days` (default 365), `governance.veto_ttl_days` (14), `governance.min_shadow_samples` (default 100), `governance.max_complexity_delta` (default tuned in PR-D) (S4).

### Near-miss hooks (each inside a `transactionSync` with the write that records the loss) (S3)

- `decideTrial`: wrap check, trial write, history and near-miss in `transactionSync`; **validate** that `winnerId` is a participant and the trial is not already decided (409 otherwise); the loser gets a `trial_loss` row.
- Tournament losers ("eliminated") are written by `applyTournamentWrite` (`tournament.ts:508+`), not `decideTrial`: hook there by diffing old vs new `candidates[].status` (`tournament_loss`). `applyMergeTrainWrite` likewise for `train_drop` (diff of the candidate list).
- `rollbackHead` (`:3530-3552`, already in the caller's transaction) writes `slo_rollback` for `head.candidateId`.
- Gate `fail`: `upsertGateVerdictSummary` (in the caller's transaction) writes `gate_fail`, deduped on `(candidate_id, 'gate_fail', run id)`. Near-misses are facts at a point in time: a later pass on a re-run does not delete one.
- `GET /api/near-misses?specId=&candidateId=` is a **read-scope** route (N1).

### Change-type classifier

- `workers/shared/change-type.ts`: pure `classifyChange({ paths?, text? }) -> { changeType, confidence, signals }`, rule-based: lockfiles/`package.json` => dependency-change; `wrangler.toml`, `.github/`, `Dockerfile*` => infra; `auth`/`secret`/`token`/`principal` paths => security-sensitive; docs/comments only => typo-fix; tests only => refactor; default behavior-change at low confidence. With no `paths` confidence caps at 0.5 and any security keyword hit selects security-sensitive (fail stricter). Table-driven test per rule.
- `POST /api/classifications` (keyed) stores a result; `GET /api/classifications?entityType=&entityId=` returns the newest. The DO validates shape (strict zod) and never classifies itself.
- **Which classification the rule reads for a candidate promotion (S6):** the candidate's own newest row, else its spec's, else the linked issue's, else `unclassified`. Callers in this plan: issue creation (text only) and the gate worker after a pre-merge verdict (best effort: a 404/5xx from an old DO is logged and the gate continues). A changed-file source for the gate is step 0 item 2.
- `unclassified` is critical in `enforced`, non-critical in `bootstrap`; the check reads at promotion time, so flipping the mode changes how old candidates are treated (N2).

### Two-person rule

**Who may approve (B1).** All of the following, checked by the DO:
- `actors.type = 'human'`, `role = 'maintainer'`, a **non-empty `github_user_id`**, not a service actor, and the principal not in `capped` (non-maintainer-scope) mode;
- the approver id comes from the **user-token-derived `X-Actor-ID`**, never from the request body;
- `POST /api/approvals`, the policy route and the role-change route are **DO tier-2 admin routes** (added to `ADMIN_PATTERNS`, `workers/shared/spec-do-auth.ts:~95`; without this any worker holding the tier-1 token could call them) and the **edge refuses `principal.kind === 'master'` on them**, allowing only `kind = 'user'` with the maintainer scope. "Edge scope maintainer" therefore means a user token, not master.
- **`enforced` mode must not be enabled until OPS "master stage 2"** (master can no longer act as a human) **and PR-F** (below) have landed; the policy route rejects `enforced` until both are recorded as done. Otherwise `enforced` is theatre: a master-token holder can mint two sock-puppet humans with GitHub ids.

**How many (B3) [decision needed].** Rev 1 required two distinct humans, neither the initiator nor the promoter, which makes a three-person rule (with exactly 3 maintainers, one absent maintainer blocks any critical change) and contradicts M5-PLAN (:60, :156, :170-171: two distinct maintainers, no initiator exclusion; a founder may provide both in bootstrap). Rev 2: **two approvals from two distinct humans; the initiator may be one of them.** In `bootstrap` with one maintainer the founder provides the approval and the row is `self_approval = 1`; the unique constraint allows one row per (candidate, rung, commit, approver), so "both approvals by the founder" is recorded as one self-approved row plus a `governance_events`/history marker `two_person: bootstrap, self-approved`, not two rows. `self_approval = 1` means: approver equals the candidate's creating/promoting human, or only one eligible human maintainer exists. A stricter separation of duties (approver may not be the initiator) is a later policy flag, only sensible with five or more maintainers.

**Reject is a veto for critical types (S1).** A standing `reject` (not superseded by the rejecting maintainer's own later row) blocks promotion of a critical change in `enforced` mode; only that maintainer or break-glass can clear it. In `bootstrap` it is recorded and does not block.

**When approval is needed.** The latest classification is in `governance.critical_types`, or `unclassified` in `enforced`. The rev 1 "low trust (< 90) needs two approvals" trigger is **dropped until M5b** (B2, N3): there is no trustworthy promoting actor (see Facts), every actor sits at trust 50, and trust is master-writable and unvalidated, so the trigger is vacuous or exploitable today. Decision 3 from rev 1 therefore resolves as "not applicable until trust is calibrated".

**The hook (B2, S3, S5).** One DO method `assertPromotionApprovals(candidateId, rung)` called inside the `transactionSync` of every path in the inventory table (hook sites 1, 3/4 via `createPromotionState`/`patchPromotionState`, and the deploy-ref `full` move; 2 and 5 reach it through 1 and 3/4). Check, write, history and near-miss share the transaction, so a throw leaves no partial write.
- **Bootstrap: the hook cannot throw.** It wraps its own reads and writes in try/catch that logs, never fails on a missing actor row (`'promotion-worker'` and ledger calls have none), and never blocks. A missing approval proceeds and writes `approval_missing` (candidate history).
- **Enforced:** a missing approval, or a stale one (`commit_sha` differs), rejects with 409 `{code: 'approval_required', need, have}` via a new `ApprovalRequiredError` mapped in the main catch (`index.ts:4557-4567`, which today maps only `ConflictError` to a bare message) and in the ledger-route handlers (each maps errors itself, `:2728` style).
- The allowlist test (Risk 1) lists paths 1-9; a new writer of `promoted`/`full` fails the test until it is added and hooked.

### Idempotency and edge

`POST /api/classifications` and `POST /api/approvals` join `IDEMPOTENT_ROUTES` (an exact set, `index.ts:41-46`); the edge adds `idemKey` to the two new handlers (it is per-handler, not a list). Policy and role-change routes are not keyed (they are idempotent by value). A new edge call to `/api/approvals` or `/api/classifications` that gets the old DO's generic 404 must map it to 503 "feature unavailable" (the user-token precedent, `spec-do-auth.ts:~42-50`), never to an empty list.

## Governance continuity: a departing or malicious maintainer [decision needed]

Rev 1's automatic fallback to `bootstrap` below three active maintainers **fails open** and was a bypass (B4): one maintainer going inactive (or letting a 90-day user token lapse, or being deactivated by a master-token holder) dropped the DO to self-approval with nothing detectable. Rev 2 replaces it:

- **No automatic fallback.** If the number of active approvers drops, `enforced` stays on. Non-critical changes keep flowing (they need no approval). **Critical changes need a new eligible maintainer or a break-glass call**; they never fall back to self-approval.
- **`enforced` precondition, verifiable from stored data.** At least **two other** eligible maintainers (human, github-linked, role present) besides the setter, each with an `approvals` row inside `governance.approval_window_days`. "Active" is evaluated inside the same transaction as the check, from stored data only: role present and a recent approval row. Token liveness and "commits" are not used (commits are not in the ledger; token lifetime is 90 days, so a passive lapse would silently deactivate a maintainer).
- **Departure.** Removing a maintainer is a `role_change` that, once `enforced`, needs the same two-approver quorum; so one maintainer cannot demote the others, and one maintainer cannot relax the policy alone (policy changes need the quorum too). Until PR-F ships these are single-maintainer actions, which is why `enforced` is blocked before PR-F (S1).
- **Break-glass.** The master token can set `bootstrap`, grant a maintainer role, or finish a stuck promotion. Each call needs a **mandatory reason** (400 without one) and writes a `break_glass` row to `governance_events` with the master caller's asserted `X-Actor-ID`, the request id and the reason, plus an alert (a log line a Workers Logs alert watches), not just a log. Honest limit: the plan cannot enforce "human-only" on the master token, because every worker holds it; the control is OPS master stage 2 and the reason that the Cloudflare account owner is the root of trust anyway. Residual risks: the account owner can always override; two colluding maintainers can approve; stolen maintainer tokens (mitigation: revocable user tokens and an audit trail). A cooling-off delay on critical approvals is a follow-up.
- **Why this addresses the maintainer's concern.** A departure never silently weakens the rule and never freezes non-critical delivery; a stuck critical change has one explicit, logged recovery path through the account owner; and a single malicious maintainer cannot promote a critical change alone (needs a second human), cannot remove or demote others alone, and cannot relax policy alone, once PR-F lands.

## Mixed-version window (one push deploys all ten workers)

- DO new, callers old: the tables are unused by old callers; bootstrap never blocks, so old promotion-worker calls keep working.
- Callers new, DO old: new routes answer a generic 404; classification and near-miss readers treat it as "not available yet" (logged), approvals map it to 503; nothing treats it as empty data (AGENTS.md `Response.ok` rule).
- No existing request or response shape gains a field (strict zod); all new data uses new routes and tables.
- Rollback to a pre-m14 DO leaves the tables and ignores them (rollback floor), because they reference `actors` only.

## Rev 3 amendments (supersede conflicting text above)

**B1, classification cannot be downgraded or stale.** `change_classifications` carries `commit_sha`. The effective criticality at check time is the **maximum strictness** over all rows for (candidate, current head sha), the spec row and the linked issue row; with no row for the head sha the result is `unclassified`. `classifyChange` returns `unclassified` (not `behavior-change`) when it has no `paths`. Writing a less strict row than one already present for the same entity is a maintainer-only route; the gate worker's tier-1 token can only add rows at equal or greater strictness. A **changed-file source for the gate** is an `enforced` precondition (step 0 item 2), because the gate receives shas only.

**B2, eligible approver is provable from stored data.** In addition to the rules above, an approver needs a `user_tokens` row with `created_via = 'session'` (GitHub OAuth login) for that actor, and the request's token must be one such token (the edge forwards `X-Beehive-Token-Id`). Master-minted (`created_via = 'admin'`) tokens never count for approvals or quorum. A break-glass role grant is stamped `role_origin = break_glass` in `governance_events`; approvals from such an actor count only after a quorum of non-break-glass maintainers ratifies the role. "Master stage 2" is defined in OPS as: master cannot create human actors, grant the role or mint user tokens except under break-glass. Its "done" state is a **deployed `wrangler.toml` var** (`GOVERNANCE_MASTER_STAGE2`, human deploy only), not a runtime setting master could write (which would be circular).

**B3, supersession and quorum storage.** Fixed in the `approvals` definition above (no unique key on `decision`; `subject_type`/`subject_id`). A role or policy change applies when at least 2 distinct eligible approvers hold a row for its request hash created within 7 days.

**S1, the DO must see the principal kind.** On the three admin routes (approvals, policy, role change) the edge sets `X-Beehive-Principal: user` and `X-Beehive-Token-Id`; trust is valid because only the edge holds the admin token. In `enforced` the DO fails closed (403) when the header is absent (old edge, new DO); in `bootstrap` it proceeds and records `unverified`. Today the role route is master-only (`workers/api/lifecycle.ts:73`) and `authorize()` blocks user tokens on `/api/admin/*`, so this reverses the current rule: add **PR-D0**, opening the role, policy and approvals routes to maintainer-scope user tokens (`USER_MAINTAINER_ROUTES`). Master stays allowed only under break-glass with a mandatory reason, which also prevents a first-maintainer deadlock.

**S2, `self_approval` and the satisfied predicate** are defined from stored data only: `self_approval = 1` iff exactly one eligible human maintainer exists at insert time; `required = 2` in `enforced`; in `bootstrap` the hook writes `approval_missing` iff effective approvals < min(2, eligible count). The initiator clause is dropped (there is no data source). Marker text: `two_person: bootstrap_single_maintainer`.

**S3, hook and transaction conditions.** (i) Gate only on **entering** `promoted` or completing at `full`; never gate rollback, `rolled_back`, `failed` or same-state writes; `patchPromotionState` is gated only when the merged row is `completed` at `full` and the prior row differs. (ii) Wrapping `transitionCandidate` in `transactionSync` turns today's no-op for an unknown id (history row, then a handler 404) into a thrown `NotFoundError`; map `NotFoundError` and `ApprovalRequiredError` in the main catch (`index.ts:4557`) so a 404 does not become a 500. ## Rev 4 amendments: untrusted-origin intent (supersede conflicting text above)

**Trigger.** The maintainer raised the case where an untrusted user creates an issue or spec that leads to vulnerable code reaching live traffic and customer data. The oracle ladder cannot catch it: a spec that asks for harm makes the harmful code conform, and a backdoor that fires only on attacker-controlled input does not show in shadow or canary. The rev 3 position "approval gates `full` only" is **wrong for untrusted origins**, because real data reaches candidate code at the first mirrored-traffic rung, before `full`. This amendment adds an origin dimension and moves the human gate earlier for untrusted origin.

**What was verified in code (2026-10-31).** In place today: UI login is limited to `ALLOWED_GITHUB_USERS` (`workers/api/ui.ts:323`) and `POST /api/issues` needs an authenticated principal (`workers/api/principal.ts:271`), so no untrusted user can create intent through the UI; the build sandbox has `enableInternet: false` (`workers/sandbox-runner/build-sandbox.ts:105`) and the test sandbox has no network apart from an npm-registry gateway (`test-sandbox.ts`); mirrored requests to candidates carry only an allowlist of headers, never `Authorization`, cookies or `X-Actor-ID` (`workers/shadow-router/candidate-headers.ts`); mirrored targets must be https `workers.dev` hosts (`shadow-router/config.ts:243`); candidate Workers are uploaded as `beehive-candidate-<id>` with `bindings: bundle.bindings ?? []` and the comment "default none: candidate services are stateless", and reserved platform names are refused (`preview-manager/versions.ts:41-47, 204`). **Not in place:** (1) the **mirrored request body** (customer data) goes in full to every candidate; (2) a deployed candidate Worker has **default outbound network access** (a plain Worker cannot be egress-restricted; Workers for Platforms with an outbound worker could, and is listed under Future/Optional, blocked on a paid tier), so a malicious candidate can send mirrored bodies anywhere at the shadow rung; (3) no origin trust or intent approval exists; (4) I did not find code that sets `bundle.bindings`, so I could not confirm no path adds bindings, and the reviewer must check.

**Origin trust.** `intent_provenance` records `origin` for every issue and spec, derived **by the DO from the authenticated principal**, never from the request body: a session user token whose actor is an eligible maintainer (E, rev 3) => `maintainer`; the master token => `maintainer` with `source = 'api'` and a `governance_events` note; a registered service/agent token => `known_agent`; any other authenticated principal or a GitHub-sourced issue => `external`; a request through an old edge that sends no principal header => `unknown`, treated as `external` (fail closed; a maintainer approval of the spec clears it). Origin is monotone for a spec derived from an issue: the spec's origin is the **lower** of its own and its source issue's.

**Intent approval (new state machine (e), in `docs/GOVERNANCE-STATE-MACHINES.md`).** A spec whose origin is not `maintainer` is `draft` until a human approves it: an `approvals` row with `subject_type = 'spec'`, `subject_id` = spec id, `content_hash` = sha256 of the spec content at approval; the approver must be in E. Any later change to the spec content invalidates the approval (hash mismatch). **Enforced from day one, in `bootstrap` and `enforced` alike**, because it is a security control and nothing external exists yet to block. The DO refuses `POST /api/candidates` for a non-approved non-maintainer-origin spec with 409 `spec_not_approved`.

**Real-data eligibility (new, the earlier gate).** A candidate is *real-data eligible* iff its spec origin is `maintainer` or its spec has a valid intent approval. The Spec DO exposes `GET /api/candidates/:id/exposure` (read scope) returning `{eligible, reason}`. Every path that sends real traffic or data to candidate code must consult it and, for an ineligible candidate, send nothing or send only a synthetic or redacted body: the shadow router's targets, the scientist comparator and `triggerShadowComparisons` in preview-manager, the canary splits and the deploy-ref `canary` and `full` moves. **Step 0 item 4 (new, before PR-D0):** inventory every such path with file:line, as was done for the `promoted` writers. Defence in depth: the DO also refuses `PATCH /api/candidates/:id/stage` into `passed_shadow` and later for an ineligible candidate (log-only first, like the other stage rules), and the deploy-ref move refuses ineligible candidates. Mixed-version: an old router or old comparator ignores the endpoint, so the DO-side refusals are the control that holds during the window; the router adopting the check is best effort until fully deployed.

**Egress (residual risk, stated plainly).** Until candidate Workers can be egress-restricted (Workers for Platforms outbound worker, or a Cloudflare-side control), an *eligible* candidate with malicious code can still exfiltrate mirrored bodies. Mitigations in this plan: intent approval and the types below force a human before real data for untrusted origin; mirrored bodies for non-`maintainer` origins are redacted or synthetic until eligible; PR-D adds a best-effort gate check that flags `fetch(` to hosts outside an allowlist (advisory, not a control). The follow-up is a WfP spike (dispatch namespace plus outbound worker) and a decision to run all candidates only there.

**New change types and the weak-evidence trigger.**
- `schema-migration` (Spec DO schema, `schema.sql`, `runMigrations`, any `ALTER`/`DROP`): irreversible, breaks "rollback is a ref operation" (rule 7).
- `oracle-change`: edits to specs and delta surfaces, gate and test code (including tests *inside the candidate*), the classifier, the state machines and governance code. If a candidate edits what it is judged against, the ladder measures itself. This is the strictest type: it also requires approval at the first real-data rung, not only `full`.
- `dependency-change` is widened beyond `package.json`/lockfiles: base images in `Dockerfile*`, `compatibility_date` and flags in `wrangler.toml`, CI action versions.
- **Requirement level** = max of change type, origin and evidence. A candidate is **evidence-weak** (and needs the critical requirement) when the shadow sample count is below `governance.min_shadow_samples`, the canary evidence source is `shadow` only (the case today), the complexity delta exceeds `governance.max_complexity_delta`, or the author agent has no promoted candidate yet. Weak evidence never lowers a requirement. Computed at check time from stored data.
- Approval points by origin: `maintainer` origin: `full` only (rev 3); `external`/`unknown` origin: the intent approval before any candidate exists, **plus** a candidate approval before the first real-data rung for critical or evidence-weak candidates, plus `full`.

**Agents treat issue text as data.** The spec is produced by a trusted triage step (a maintainer or a `maintainer`-origin agent), not by the implementing agent reading the raw issue. This is a convention enforced by the intent approval above (the human approves the spec the agent will implement, not the issue), and recorded in `docs/AGENT-ROUTING.md` as a rule for implementer prompts (a docs change in PR-D0).

**Cost and runaway generation.** Origin `external` creation is rate-limited per principal (already planned under M5 section E, "agent authorization for issue/spec creation") and is **not enabled** until that exists: the allowlist stays the only door. Opening untrusted creation is a separate maintainer decision recorded in OPS, with these controls as prerequisites.

**PR slicing additions.** PR-A's m14 definition gains `intent_provenance`, the two change types and `approvals.content_hash`/`subject_type 'spec'` (already edited above). New **PR-G, intent provenance and exposure**: DO-side provenance writes with the principal header, spec intent approval, `spec_not_approved` refusal, the exposure endpoint, DO-side stage and deploy-ref refusals (log-only first for stage), router and comparator checks. PR-G needs the Step 0 item 4 inventory and ships before untrusted creation is ever opened. PR-D's requirement-level computation uses the origin and evidence inputs.

**Open items (maintainer):** 7. Origin `master` counts as `maintainer` (the operator holds it): confirm. 8. Untrusted creation stays closed (allowlist only) until PR-G, the egress decision and issue rate limits exist: confirm. 9. Mirrored bodies for non-maintainer-origin candidates are redacted or synthetic until eligible: confirm, and say which fields count as customer data for this platform.
